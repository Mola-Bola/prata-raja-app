# Attack-window inventory

Read-only source inventory for the next combat-feel decision. No mechanics changed; no phone/browser proof was run.

## Source facts

- **Normal melee contact has no intentional windup or recovery in simulation.** In `src/core/sim/enemies.ts`, a walker reaching `FIELD.reachY` (30) is clamped there and changes to `state: 'attack'`; because the state switch calls `walk()` once per update, `contactDps * dt` begins on the next update. `contact()` checks counter reach, not horizontal distance from Kannan, so current melee is counter-breach pressure and lateral movement alone cannot dodge it. Aggregated `playerHit` contact events flush every 0.5 s. Knockback moves enemies upward; the next walk tick returns them to `walk` if they are beyond reach. There is no per-enemy damage cooldown or lunge-only hitbox. Exploders are the exception: on reaching the counter they enter `fuse` for `def.explode.fuse`, then blast if Kannan remains within radius.
- **Ranged enemy tell exists.** A shooter/healer parks in `holdY`; shooter emits `aim` when starting `aimTime`, snapshots Kannan's x into `_tx`, then fires after the timer. Projectile flight continues the threat. `src/core/sim/danger.ts` exposes enemy shots and shooter aim as danger windows. Existing tests at `src/core/__tests__/sim.test.ts:497` and nearby cover aim/fire, dodging/hold behavior, and explosions/contact.
- **Boss windows are separate and already telegraphed.** Boss tell/charge/sweep/rain/etc. timing lives in `src/core/sim/boss.ts`; `dangers()` includes tell/charge zones. The parked slow-boss change `5a4a12e` remains a failed balance experiment and is outside this inventory's recommendation.
- **Concurrent melee attacks are not budgeted/capped in current source.** Every alive enemy in `attack` calls `contact()` each update; damage therefore stacks with attacker count. The existing contact test at `src/core/__tests__/sim.test.ts:579` explicitly proves two melee attackers stack their DPS; `w.budgetLeft` is wave spawn budget, not a simultaneous-attacker budget. `src/core/sim/throw.ts` does prioritize `state === 'attack'` targets, including bomb clusters, but that is target selection rather than an attack token system. Roadmap's “attack tokens” is future work.
- **Renderer readability starts after counter reach, not before the first contact tick.** `src/game/phaser/actors.ts` starts a 0.16 s visual lunge while `state === 'attack'`; after that it derives a small anticipatory squash from shared `w.contactT`, which is the 0.5 s aggregate damage flush timer. This motion does not gate simulation damage and is not a per-enemy warning. `src/game/phaser/danger.ts` draws the red counter-edge pulse and `!` badge for every enemy already in `attack` state. The renderer has no normal melee pre-hit tell/recovery cue. Shooter aim and boss lanes have distinct tell/telegraph rendering elsewhere.

## Tuning seams and meaningful tests

- Smallest core seam: `src/core/sim/enemies.ts` `walk()` / `contact()` around the reach transition. A bounded proposal could add an explicit per-enemy contact-window timer/state there, keeping all timing deterministic in core. A tell can offer time to kill, knock back or control the breaching enemy under current rules; it cannot promise that a lateral dodge avoids contact. Adding player-relative bite geometry would be a separate rules change. Avoid changing boss movement or existing projectile paths.
- If the hypothesis instead limits simultaneous contact damage, the seam is also `contact()`/`updateEnemies()` plus per-world state in `src/core/types.ts`; source currently has no token counter. Don’t describe the existing wave `budgetLeft` as such.
- Renderer seam for a core event/state is `src/game/phaser/actors.ts` and `src/game/phaser/danger.ts`; align cue to the actual timing/state rather than inferring from `contactT`.
- Existing behavioral test homes: `src/core/__tests__/sim.test.ts` around 563 (exploder), 579–600 (contact and reach), 497–530 (shooter), plus its later deterministic/collision regression cases. A meaningful new test should assert exact event/damage timing across substeps, knockback interruption, multiple enemies, and deterministic replay; if a visual cue is added, test the state-to-cue mapping or a focused renderer behavior. No tests were run for this inventory.

## Smallest next-feel hypothesis (proposal, not adopted)

Prototype a **brief, readable pre-contact tell for a normal enemy breaching the counter, with a short recovery beat**, using deterministic core timing and the existing small lunge cue as a visual anchor. The tell would give the player time to kill, knock back or control the breaching enemy; under current contact rules, it does not create a lateral dodge window. Changing to player-relative bite geometry would be a separate mechanic. Measure the single change against current seeded runs and inspect in browser/phone before tuning or adopting; separately investigate attacker caps only if crowd-pressure evidence points there. This is a proposal grounded in the gap between counter-reach state and post-reach rendering, not proof that the current feel is bad or that a particular duration is right.
