# Earned dip simmer: first playable contract proposal

Status: ADOPTED BOUNDED IMPLEMENTATION PLAN (ledger50), not shipped. The lead retained the three-dip pilot, separate persistent simmer, actual-use rolling cap, compatible collection/results and explicit quality deferral; the generic direct-roti-damage proposal was rejected. Exact balance numbers below remain tuning proposals pending verification. Read-only design packet for ledger 47. Inspected working repository HEAD `e52c912` on 14 October 2026; inventory baseline was `3ce28fc`. The read-only design packet was verified as ledger47; this tracked copy records the implementation decision. No progression implementation or validation is claimed by this plan.

## Recommended slice

Ship earned simmer for the three currently linkable support dips: Fish Curry, Mint Chutney, Condensed Milk. Give each a persistent recipe entry, progress from linked combat use, a small measurable next-run benefit, stall collection rows, and a result receipt. Keep other dips visible in the collection with their existing effect/availability, without showing a fake XP bar. Say explicitly that simmer currently applies to linked support dips. Do not unlock previously unavailable recipes or introduce persistent equipped dips: existing card picks still acquire dips during each run and the first two supported picks still auto-link to the signature.

This reaches an earned gameplay loop with only three established linking mechanics. Extending every global/buff/kill-trigger dip would require heterogeneous attribution and new balance work; that is a separate increment. Links currently require the signature system (stall level 9), so this pilot starts there. On a pre-signature save the collection must plainly explain “At stall level 9, matching dip picks link to your signature roti and start earning simmer XP.” Keep this explanatory copy visible, with no fake disabled simmer action. The first upgrade may therefore be distant for a fresh save; measure time to signature separately from the 40 credited-use seconds for level 2. The lead should keep that gate for this slice; changing early progression would be a separate decision. Collection access should be available without waiting for the gated recipe-book hotspot.

## Concrete proposed numbers and semantics

- Runtime `OwnedDip.level` remains 1–5, indexing the existing five content effects. UI calls it “Run tier” where disambiguation is needed. Persistent simmer is a separate 1–20 value, never an index into `DipDef.levels` and never an evolution prerequisite.
- Persist cumulative `dipXp: Partial<Record<DipId, number>>` in SaveV2. A missing entry means XP 0 / simmer 1. Derive simmer from total XP; avoid saving both level and XP with contradictory values.
- XP cost from simmer L to L+1: `40 + 10*(L-1)` for L=1…19. Total cap 2470 XP. Level 2 costs 40, level 3 cumulative 90, level 4 cumulative 150. A dip used for a sustained minute should reach its first level in one ordinary paid run; this target requires measured hit cadence before adoption.
- Earn 1 XP for an eligible linked-roti combat hit, at most once per dip per rolling 1.0 simulation second, at most 120 XP per dip per run. Initialize last-credit time only on a qualifying hit; never backfill time before acquisition. Use simulation time, not wall time, frame count, result.time, total kills or elapsed time since the run started. Multi-target blasts/volleys/orbits count once in that second; RNG draws are unchanged.
- Eligible means: ordinary earned run; the dip is currently owned and linked; hit bread belongs to the linked bread's base/evolution family; current bread/dip tags match; a living enemy takes positive direct bread HP damage. A lethal direct hit counts. Fully shield-blocked hits, enemy shots, secondary chain/death-blast damage, pure DoT ticks, misses, gaps without hits, pauses, menus and Kitchen grant nothing. Excluding the armour-pierce shield branch in the first slice is acceptable and should be documented/tested; otherwise count only its positive through-HP damage with the same limiter.
- A matching linked dip enhances exactly one minor-skill field by `1 + 0.005*(simmer-1)`, applied once AFTER the existing matching-tag effect transformation. Fish Curry scales burn `dps` only; Mint Chutney scales chill `time` only; Condensed Milk scales sugar `slowTime` only. Simmer 1 is identity, simmer 2 +0.5%, simmer 10 +4.5%, simmer 20 +9.5%. The existing matching 25% bonus retains all its current fields; this new scale touches only the selected field. Each dip transforms its own effect once, never another dip or roti damage. No scaling of Fish burn duration, Mint slow strength/freeze duration/freeze threshold, or Milk slow strength/stack duration/stack count/DoT/crash stun. Global/mismatched effects, counts, player stats and secondary effect creation retain baseline behavior. At max, selected fields are base ×1.25×1.095 = base ×1.36875, not base ×1.345.
- Power is frozen at run-start from the saved XP snapshot. Credit gained this run pays on results and benefits the next run, preventing in-run level feedback and preserving deterministic replay. A +0.5% first step is small but real; the collection/result receipt must expose the flavour-specific number. If owner play says that is imperceptible, retune the coefficient only after effect-specific balance evidence.
- Run payout follows existing MIN_PAID_WAVE=2: an early wave-1 exit pays no dip XP. All eligible credited use in a paid run counts, including wave-1 use, regardless of later victory/loss. A dip acquired one second before ending can receive at most one XP, never credit for previous waves. No participation means no progress. There is no gold/material purchase, offline accumulation, timer, reroll, fail chance or empty “simmer” button.

## Identity-preserving benefit: verified status behavior

`src/core/status.ts:applyHitEffect` confirms all three proposed fields affect real runtime behavior; a small pure `simmerEffect` helper should take the already-tag-bonused effect plus derived simmer and return an immutable copy changing only the selected field. Call it in the matching linked branch of `hitEnemy`, after the +25% transformation and before `applyHitEffect`. Do not change status logic or mutate content rows. The coefficient is bounded to [1,1.095]; omitted loadout/invalid simmer is identity. All three family distinctions survive: stronger burn, longer chill memory, longer stickiness.

- Fish: burn refresh retains `max(existing time, effect.time)` and `max(existing DPS, effect.dps)`. `tickStatuses` integrates DPS over the remaining live time and applies existing `dotPct`. Tier 1 matching baseline is 3.75 DPS for 3.75s; max simmer is 4.10625 DPS for the SAME 3.75s. A stronger earlier burn can dominate a later lower-DPS application; this existing max rule must stay unchanged. Never scale an already-simmered enemy status on refresh, otherwise repeated hits compound.
- Mint: chill `time` is overwritten on each qualifying hit and controls how long chill stacks/slow survive between hits. Tier 1 matching baseline is 7.5s; max simmer is 8.2125s, with identical 0.1 slow per stack and identical matching freeze time 1.25s. Reaching three stacks consumes chill and attempts `applyCc`; longer stack memory can indirectly make a later hit reach freeze, which is the intended modest benefit. Fast repeated attacks already refresh chill or consume it, so the benefit mainly appears after gaps; it is not longer continuous freeze. Immunity, elites/boss handling and no-extension CC behavior stay intact. Collection says “+9.5% chill duration”, not “+9.5% freeze”.
- Milk: sugar `slowTime` becomes `sugarSlow.time` via max refresh; tier 1 matching baseline is 2.5s, max simmer 2.7375s. `slowPct`, sugar stack DPS, stackTime=8, crashAt=5 and existing matching crashStun=1.25s are unchanged. Important wording correction: `sugarSlow` is NOT removed when Sugar Crash consumes the sugar stacks, so the existing sticky slow may outlast the crash. The proposed field is meaningful, but describing it as “pre-crash only” would imply a behavior the code does not have. Recommend “sticky slow duration”; preserve existing persistence through crash rather than introduce a new rule to make the phrase literally true. Lead's intended single-field restriction is satisfied.

### Fish copied burn / Sambal contract

Recommend baseline copied burn, no new provenance machinery in this slice. `sambalBlast` already copies `content.dips['fish-curry'].levels[fish.level-1]` (or default 3 DPS/2s), bypassing the linked-tag transform. Preserve that path exactly: Sambal's spread cannot inherit earned simmer or matching +25% from whichever bread happened to kill the source. It creates BASE runtime-tier Fish burn on newly ignited neighbours. This makes scope precise: “stronger burn from matching linked-roti hits,” not “all burn everywhere.” It avoids silently buffing a global spread ability when the earned dip is explicitly linked to one roti.

An already-burning neighbour retains max DPS/duration on baseline refresh; if a direct matching hit previously placed boosted Fish burn there, baseline Sambal does not downgrade it. That retention is existing status merge behavior, not propagation of boosted burn from the source. No source enemy status should be read to construct neighbour burn, and Sambal does not award dip-use XP. A future spread-provenance feature would need explicit source data/caps; do not retrofit it here.

## Flake cadence

The lead reports a flake fixture with roughly three times the hit opportunities. That is contextual evidence from the lead, not a measurement this read-only packet ran. A raw hit-count XP scheme would turn flakes, fragment bursts and AoE into progression accelerators and bias choice away from slower lob builds. The proposed rolling one-second successful-use limiter plus per-run cap makes 3x hits within the same cadence window worth the same single credit. Credit must route through one shared limiter at the successful direct-hit boundary; each fragment target, splash target and orbit bite can call it safely. It cannot be incremented on throw creation or once per target without the limiter. Extra flakes can improve uptime during gaps, so they can still raise total earned XP up to the common ceiling; measure that remaining difference in the 300-seed comparison and use thresholds/ceiling to tune it, not separate XP tables for every bread. Test identical initial hit followed by three fragment hits in <1 second yields one credit, and repeated bursts across successive seconds produce one per elapsed qualifying second. Use rolling time (last credited hit +1.0), not integer-second bins, to avoid two XP from hits straddling a boundary within milliseconds.

## Quality decision

Explicitly defer quality 0–20 to the next design increment. The broad docs call it exploratory; simmer + collection + meaningful reward is a coherent first slice without inventing an aging economy. Do not display an overnight timer or spend control, and do not save a redundant quality=0 field merely to imply shipped support. A future optional per-dip quality map can default missing entries to zero without a SaveV3 migration. That increment needs a distinct earned ingredient source and a distinct, bounded flavour effect, with no offline timer spending or conversion of XP into another grind. This recommendation does not retire quality from the direction.

7. `src/meta/runRewards.ts:applyRunResult`: deterministically add validated/capped reported XP only for supported dip IDs present in final `result.dips` with a matching linked bread family in final `result.breads`. 9. `src/game/ui/stall/Rewards.tsx`: render earned receipts from payout only; never derive awards or write save from UI. At most two eligible linked rows: “Mint Chutney · +54 simmer XP”, “Simmer 1 → 2 · +0.5% chill duration”, plus next threshold. No rewards row when zero was earned.

11. `src/game/ui/stall/StallHub.tsx` has explicit signature/settings sheets plus existing recipes hotspot. ## Acceptance and meaningful validation for implementation

- Migration: existing V1/V2 saves round-trip unchanged outside the new default map; partial corruption recovers per dip; unknown IDs/XP types cannot unlock content; threshold/cap handling and no contradictory level field.
- Accounting scenarios in deterministic core: acquire after a long run then immediately end (0); acquire, land one late hit then end (at most 1); 40 eligible seconds cross first threshold; one AoE hit touching 20 enemies/volley/orbit stays once per rolling second; no-hit running/pauses/DoT/chain/fully blocked shields do not earn; mismatched tags/other roti do not earn; evolved linked roti still earns; each of two linked dips has its own limiter; 120/run and 2470 lifetime caps; no additional RNG draws; split dt boundaries produce identical credit.
- Benefit tests: absent map / simmer 1 matches baseline exactly. For each runtime tier1–5 verify matching+max simmer changes ONLY Fish dps / Mint time / Milk slowTime by ×1.095 after the existing ×1.25 tag bonus; direct bread damage and all other fields remain byte-equivalent. Global/unrelated/mismatched effects and unearned callers remain baseline. Repeated application must not compound or mutate content. Confirm lethal direct hits credit before secondary processing.
- Status behavior tests: single Fish hit then no refresh integrates exact +9.5% burn DPS over unchanged time and dotPct; lower-DPS refresh preserves previous maximum rather than multiplies it again. Mint hit, gap 7.6s, hit retains the first stack only at max simmer versus matching baseline; the third hit can freeze but freeze duration, slowPerStack, threshold and immunity stay unchanged. Milk sugarSlow still exists for 2.6s at max versus expired baseline; speed reduction is unchanged while present, crash threshold/stun/stack DPS remain identical, and sticky slow survives crash as before.
- Sambal tests: source carrying boosted Fish burn ignites fresh neighbour at raw runtime-tier Fish DPS/time, regardless of saved simmer/linked tag; absent Fish keeps default3/2. A neighbour with a previous directly-applied stronger burn retains max DPS/time on baseline spread refresh. Secondary spread earns no XP and never reads source status provenance.
- Payout: paid victory/loss persists exactly reported use; missing map zero; wave-1 exit zero; receipt before/after matches save; duplicate GameUi runEnd leaves one award and Kitchen never produces save changes. Demonstrate computeLoadout snapshot isolates current run from newly granted XP.
- Phone web: 360px viewport, no horizontal overflow, collection reachable on a legacy save, normal unlock labels, readable numeric bar/bonus, two results rows, reload preserving progress; normal run tiers still 1–5. Kitchen run/end/restart leaves complete real save byte-equivalent.
- Balance evidence before final number adoption: compare the same 300 seeds/bot policy at simmer 1, realistic early simmer 3–5, and maximum simmer 20 with one/two matching dips. Record win rate, reached waves, boss time, burn damage, chill/slow uptime, freeze/crash counts and durations, earned XP and acquisition times by dip. This is a requested future validation plan, not run by this read-only design task. Diagnose acquisition timing/link gate if first gain takes several ordinary runs; adjust thresholds/credit cap before adding another reward economy. Simmer 1 must reproduce baseline; maximum cannot create unbounded procs or overpower unrelated builds.
